01 · Start with a research question

Not “what prompt makes the model smarter?”

The useful question is narrower and testable:

Does an observable behavior contract change how reliably an AI agent completes a defined task, while keeping the task, model, tools, context, budget, and evaluator constant?
A

Prompt

The words supplied to an agent: the task, a trigger, or a behavior contract.

B

Context

The authoritative information available to work from: files, tests, constraints, and evidence.

C

Behavior engineering

Designing observable habits—trace the cause, check the path, preserve scope, and prove the result.

The distinction matters. A trigger can name a useful behavior, but a stronger study tests the contract and its observable signals—not the aura around a phrase.

03 · Controlled experiment

Hold the world steady. Change one major variable.

R1 used five deterministic engineering bugfix fixtures, one protocol, four arms, and one trial per task/arm. The order was seeded and randomized. Each cell ran in a fresh workspace.

Success required the hidden evaluation outcome, the user goal, regression-free behavior, and scope discipline. Observable evidence counted; private chain-of-thought did not.

What R1 does not establish

Because all four arms reached 5/5 in one trial per task/arm, R1 provides no success-rate evidence that any treatment beats B0. Its token and latency differences are descriptive samples, not a general efficiency or speed ranking.

06 · R0 rejection

A rejected run can still teach you something.

R0 completed 20/20 cells with verified model provenance, but the experiment was rejected before comparison. T02 underspecified the department data shape. T05 mixed zero-based visible-test attempts with one-based task and hidden-grader expectations.

The lesson is experimental hygiene: freeze inputs, audit task contracts, and keep a repaired rerun separate. R0 metrics are not used for ranking or combined with R1.

REJECTED

Input validity comes first

Before asking which arm wins, ask whether every cell received the same, unambiguous task.

07 · Methodology

Freeze the comparison. Observe the boundary.

01

Freeze

Task specs, visible fixtures, registry, and pilot scripts are fixed within the comparison.

02

Isolate

Each candidate starts fresh with the visible task context. Evaluator implementation and reference solutions stay out of the prompt and workspace.

03

Evaluate

Acceptance, user goal, regressions, scope, observable trajectory, reliability, efficiency, and safety are scored from visible evidence.

04

Calibrate

Missing or unverifiable evidence is UNKNOWN—not PASS. Infrastructure-invalid attempts are classified separately.

Why a hidden grader?

It protects the evaluation from being solved by copying an answer. This site explains the concept and the boundary; it does not expose grader content.

08 · Learn by doing

Practical habits for better agent work

Use protocols as checklists for observable behavior, not as incantations. Start with the smallest sufficient context, trace the responsible path, make a scoped change, then rerun the real path and regressions.

Explore the harness ↗
01

Ask “what evidence would change my mind?”

That turns a plausible story into a falsifiable investigation.

02

Separate outcome from efficiency

A faster or shorter run is not useful if it changes correctness or scope.

03

Repeat before ranking

One trial can describe a sample. Repeated trials help assess reliability and variance.

Glossary

Arm
One version of the prompt or behavior framing being compared.
Cell
One task × arm × trial combination.
Protocol
A named behavior contract with a purpose and observable signals.
Descriptive evidence
A report of what this sample did, without a universal claim.
Hidden grader
An evaluator-owned test that checks the result without revealing its answer.
UNKNOWN
The status for missing or unverifiable evidence; it is not a pass.
